# Public Goose library comparisons

Research date: **2026-11-06**. Scope: Macho0x's public Goose-language libraries versus the 18 carabistouflette libraries listed below. This concerns [aardappel's Goose language](https://github.com/aardappel/goose), not the unrelated Goose AI agent or database migration tools.

Directory source snapshots and detailed comparison baselines are separate reviews.
They can cite different commits on the same date. Each comparison applies to its
explicitly linked revision; a directory pin does not imply that all comparison
claims were revalidated at that pin. Expanded Source & review shows both snapshots
when they differ. [Source inventory](sources.json).

## Findings and listing recommendations

**Include both authors where their use cases differ.** Repository names do not establish interchangeability. Macho0x adds substantial numeric, binary-format and blockchain coverage. Carabistouflette offers application infrastructure with explicit ownership, resource limits and native-backend contracts. The useful choices are workload-specific:

| Need | Recommended discovery entry | Reason and qualification |
| --- | --- | --- |
| SHA-256 and detached Ed25519 verification for downloaded artifacts | [carabistouflette/goose-crypto](https://github.com/carabistouflette/goose-crypto); link [goose-artifact](https://github.com/carabistouflette/goose-artifact) as a consumer | Explicit errors, bounded caller buffers, incremental hashing and libsodium verification. |
| Broader algorithms in Goose, including Keccak and transaction signing | [Macho0x/goose-crypto](https://github.com/Macho0x/goose-crypto) **and** [goose-signature](https://github.com/Macho0x/goose-signature) | Many additional primitives and signing formats; crypto explicitly warns that it is not constant-time. Do not present it as an audited secret-handling replacement. |
| HTTP server, routing, SSE or server WebSocket | [kaitk/goose-http](https://github.com/kaitk/goose-http) upstream; identify [Macho0x/goose-http](https://github.com/Macho0x/goose-http) as its inspected fork | Server functionality is complementary to carabistouflette's client. The fork's own quickstart imports kaitk. |
| Bounded HTTPS GET/POST and pull streaming downloads | [carabistouflette/goose-http](https://github.com/carabistouflette/goose-http) | Separate body/header limits, streaming steps and explicit transfer/HTTP success distinction. |
| Blocking HTTP client with PUT/PATCH/DELETE and reusable sessions | [The inspected fork’s optional `http.client` module](https://github.com/Macho0x/goose-http/blob/e0722c4607b2a1b9ad7edfaf3d8964a431e3714a/client.goose), preferably evaluated through upstream | This module really exists despite the server-focused description. It uses goose-tls and a different timeout/reuse contract. |
| Strict owned JSON-to-struct mapping | [carabistouflette/goose-json](https://github.com/carabistouflette/goose-json) | Rejects missing, duplicate and unknown fields. It is deliberately narrower than general JSON. |
| Ethereum integers, ABI words and JSON-RPC bytes | [Macho0x/goose-ethereum](https://github.com/Macho0x/goose-ethereum) | A protocol codec, not a provider, wallet or transport. Pairing it with a bounded POST client is plausible future integration work. |
| TOML read-only borrowed trees | [Macho0x/goose-toml](https://github.com/Macho0x/goose-toml) | TOML 1.0 parser with caller-retained source and node storage. |
| Owned TOML editing/writing or TOML 1.1 | [carabistouflette/goose-toml](https://github.com/carabistouflette/goose-toml); [goose-toml-edit](https://github.com/carabistouflette/goose-toml-edit) for source-preserving edits | Different ownership and editing requirements justify both entries. |
| Ready-made UTC process logs with heuristic secret redaction | [Macho0x/goose-logger](https://github.com/Macho0x/goose-logger) | Automatic clocks and source arguments, plus independent sanitization module. |
| Bounded escaped logs with caller-owned output and errors | [carabistouflette/goose-log](https://github.com/carabistouflette/goose-log) | Explicit sink, status and masking; no automatic secret detection. |

Evidence for these recommendations is detailed below. These are discovery recommendations, not security certification or a performance ranking.

## Method and reproducibility

The public [Macho0x repository API](https://api.github.com/users/Macho0x/repos?per_page=100&type=owner) returned 12 `goose-*` repositories, including one HTTP fork. All 12 default-branch commit snapshots were downloaded and their READMEs inspected. Targeted source and tests were read, especially crypto, Ethereum ABI/RPC, HTTP client and JSON consumers. The 18 carabistouflette READMEs were compared byte-for-byte with the public raw files at their recorded commits: all matched. Public snapshots, rather than moving branches or popularity, underpin the comparison.

“Lacks” below means absent from the inspected public library set or API. It does not mean Goose cannot implement the feature, or that no unrelated author supplies it. README test claims are attributed project evidence; this research did **not** compile packages, rerun conformance/security tests, measure performance, contact trading endpoints, or prove cross-package compatibility. Displayed README versions are not independently verified release tags. All following repository links pin full commits.

## API-level overlaps

### Crypto: overlapping algorithms, different contracts

Carabistouflette's [source API](https://github.com/carabistouflette/goose-crypto/blob/729cd08e8df2bf7d2c9c12000d6fc94e62fcb55e/crypto.goose) exposes `sha256(message, digest) -> Error`, caller-owned `Sha256` with `init/update/finish`, `verify_ed25519(message, signature, public_key) -> Error`, and strict `hex_encode/hex_decode`. Its [README contract](https://github.com/carabistouflette/goose-crypto/blob/729cd08e8df2bf7d2c9c12000d6fc94e62fcb55e/README.md) requires exact output/key/signature sizes, rejects overlapping writable/readable spans, preserves outputs/state on reported errors, and makes `finish` deactivate the state. It explicitly excludes signing, encryption, RNG and secure-memory APIs.

Macho0x's [SHA-256 source](https://github.com/Macho0x/goose-crypto/blob/0fa24f53fd6918c0cfeff6012b7352f60d480801/sha256.goose) offers `hash(data) -> u8[32]`, `Ctx` with `init/update/finish`, double-SHA-256 and incremental/one-shot HMAC. Here **`finish` snapshots the digest and leaves the context unchanged**. Its length guard aborts rather than returning the other package's `LimitExceeded`. These are migration-relevant behavioral differences, not just naming differences.

Macho0x's [Ed25519 source](https://github.com/Macho0x/goose-crypto/blob/0fa24f53fd6918c0cfeff6012b7352f60d480801/ed25519.goose) provides `public_key(seed)`, `sign(seed, msg)` and `verify(public, msg, sig) -> bool`. Verification's argument order differs, and a boolean does not distinguish malformed lengths from an invalid signature. The [tests](https://github.com/Macho0x/goose-crypto/blob/0fa24f53fd6918c0cfeff6012b7352f60d480801/tests/ed25519.goose) include known vectors and a modified-signature rejection. Those checks do not establish equivalence to libsodium's acceptance policy for every noncanonical or small-order input; that would require explicit differential testing.

Its [algorithm inventory](https://github.com/Macho0x/goose-crypto/blob/0fa24f53fd6918c0cfeff6012b7352f60d480801/README.md) adds SHA-512/HMAC, RIPEMD-160, HKDF-SHA256, Keccak-256, BLAKE3, ChaCha20-Poly1305, X25519, secp256k1, Argon2id and BIP-340. [secp256k1](https://github.com/Macho0x/goose-crypto/blob/0fa24f53fd6918c0cfeff6012b7352f60d480801/secp256k1.goose) exposes public-key derivation, RFC-6979-based signing, verification and recovery. The package explicitly says it does not run in constant time, even though some field operations mask choices. Pure Goose and published vectors are useful properties; neither establishes resistance to timing observation.

**Recommendation:** list both with explicit backend and secret-handling qualifications. Prefer carabistouflette's narrow API for its existing signed-download workflow; choose Macho0x for additional algorithms only after reviewing the relevant threat model and correctness evidence. Keep transaction formats in the separately listed [goose-signature](https://github.com/Macho0x/goose-signature/blob/2dbfd5eb625c69d26291c095a52fd5c251f13fe8/README.md) package rather than attributing those APIs to goose-crypto.

### Ethereum: new protocol coverage, not a duplicate crypto package

[U256 source](https://github.com/Macho0x/goose-ethereum/blob/f80742b76c578025618d389396e1340391cd4e65/u256.goose) uses eight little-endian `u32` limbs with checked arithmetic and 32-byte big-endian conversion. It is neither arbitrary-precision bigint nor the secp256k1 field representation. The [documented contract](https://github.com/Macho0x/goose-ethereum/blob/f80742b76c578025618d389396e1340391cd4e65/README.md) rejects arithmetic overflow, zero division and negative shifts; shifts of at least 256 produce zero.

[ABI source](https://github.com/Macho0x/goose-ethereum/blob/f80742b76c578025618d389396e1340391cd4e65/abi.goose) exposes `selector`, word encoders/decoders for address/bool/U256, dynamic bytes/string/U256-array tails and an address/U256 pair. Dynamic helpers append **tails without head offsets**: applications must calculate offsets when composing calls. `decode_address` accepts the low 20 bytes without requiring the high 12 bytes to be zero; dynamic-byte decoding checks available padded length but does not enforce all padding bytes are zero. These helpers should not be described as a full canonical ABI validator or general schema-driven ABI implementation.

[RPC source](https://github.com/Macho0x/goose-ethereum/blob/f80742b76c578025618d389396e1340391cd4e65/rpc.goose) appends request bytes for `eth_call`, `eth_sendRawTransaction`, `eth_getLogs` and `eth_blockNumber`. `result(text)` returns a decoded string or raw JSON for another non-null value; malformed JSON, any `error` member, missing result or null result returns false. It does not validate the `jsonrpc` version or correlate `id`; subsequent duplicate `result` members are skipped. It discards structured RPC error details. String arguments such as addresses, quantities and block tags are caller-supplied text rather than semantically validated Ethereum types.

**Recommendation:** include goose-ethereum under blockchain/protocol codecs. Carabistouflette's listed libraries have no equivalent U256, Keccak, ABI or Ethereum RPC layer. They do have a binary POST transport and JSON tools, so an independently pinned read-only integration is a reasonable candidate; compatibility is not demonstrated here. Transaction signing belongs to goose-signature, which lists EIP-191/EIP-712, legacy and typed Ethereum transactions, Bitcoin sighash/proofs and Solana messages. Its [scope limits](https://github.com/Macho0x/goose-signature/blob/2dbfd5eb625c69d26291c095a52fd5c251f13fe8/README.md) explicitly exclude an address codec, HD derivation, UTXO set and script interpreter. Neither package is a complete wallet/provider SDK.

### HTTP: server and client, plus a real client overlap

The [GitHub repository metadata](https://api.github.com/repos/Macho0x/goose-http) identifies the fork parent as `kaitk/goose-http`. The pinned [README](https://github.com/Macho0x/goose-http/blob/e0722c4607b2a1b9ad7edfaf3d8964a431e3714a/README.md) imports kaitk in its quickstart and describes worker event loops, routing, keep-alive, request/response streaming, files, SSE and server WebSocket support. It marks protocol/platform qualifications for TLS, HTTP/2, HTTP/3 and outbound connections. Preserve those qualifications; “HTTP supports Windows” does not imply the optional HTTPS client does.

The actual [optional client source](https://github.com/Macho0x/goose-http/blob/e0722c4607b2a1b9ad7edfaf3d8964a431e3714a/client.goose) and [API documentation](https://github.com/Macho0x/goose-http/blob/e0722c4607b2a1b9ad7edfaf3d8964a431e3714a/docs/api.md) expose `session/free`, `get/post/put/patch/delete`, arbitrary `request`, explicit headers, bearer authorization, binary `body`, `session_trusting` for a supplied CA, and a reusable same-origin connection. `Session.max_body` defaults to 16 MiB; `ClientResponse.fields` has an 8192-byte capacity. The client accumulates response bytes rather than exposing carabistouflette-style pull chunks. `Session.ms` limits **each wait**, not the total operation, and hostname lookup is unbounded by that value. The documented client does not replay failed requests, follow redirects, store cookies or decode compressed content.

`http::json(req, v)` calls `format(payload, v)` and sets the media type. It depends on the value's formatting overload; it is **not evidence of automatic arbitrary-struct JSON serialization**.

Carabistouflette's [actual API](https://github.com/carabistouflette/goose-http/blob/6dc7a9874415c8e3e5d654585696805b7f3891f3/http.goose) has `Method { Get, Post }`, `request`, `open_stream/read_chunk/close_stream`, and `open_client/request/close_client`. The [contract](https://github.com/carabistouflette/goose-http/blob/6dc7a9874415c8e3e5d654585696805b7f3891f3/README.md) separates transfer completion from 2xx success, defaults to HTTPS, requires opt-in cleartext, rejects redirects/proxy inheritance, and explicitly bounds body/header storage. Streams expose `Chunk`, `IdleTimeout`, `Done`, `Error`, `Cancelled` with distinct terminal behavior. Its optional [origin-bound reusable client](https://github.com/carabistouflette/goose-http/blob/6dc7a9874415c8e3e5d654585696805b7f3891f3/docs/CLIENT.md) supports GET, not persistent POST; libcurl may reconnect/replay stale reused GETs. Transfer timeouts are not hard total wall-clock deadlines because resolver cleanup can exceed them.

**Recommendation:** list the upstream server and carabistouflette client separately, and annotate the optional server-package client. For bounded artifact downloads, carabistouflette's streaming contract fits directly. For session-based REST calls needing more verbs or supplied CAs, the inspected optional client has concrete additional APIs. No source comparison against current kaitk main was performed, so do not claim Macho0x independently authored those features or that the fork tracks upstream exactly.

### JSON: no Macho0x goose-json repository in this survey

[Ethereum RPC](https://github.com/Macho0x/goose-ethereum/blob/f80742b76c578025618d389396e1340391cd4e65/rpc.goose) imports Goose's standard `json`, not carabistouflette/goose-json. That distinction also appears in Hyperliquid's [info parser](https://github.com/Macho0x/goose-hyperliquid/blob/b34a5be4e2a39cbc920e3af50af5bf5a042afcea/info.goose) and [exchange writer](https://github.com/Macho0x/goose-hyperliquid/blob/b34a5be4e2a39cbc920e3af50af5bf5a042afcea/exchange.goose). The inspected [upstream standard module](https://github.com/aardappel/goose/blob/7b90f91d91845f4ef1712e16ed053f395e4e6e1c/stdlib/json.goose) has both a node/member API and incremental reader/writer helpers. This upstream snapshot demonstrates the API; the Macho0x packages do not pin it, so it is not a proven compiler combination.

Carabistouflette's [codec source](https://github.com/carabistouflette/goose-json/blob/0061ec83bf7f88763402751d50e3c27f3dd13f68/json_codec.goose) layers strict owned struct decoding on standard JSON, with native helpers. `deserialize<T>` requires a struct root; `deserialize_into` additionally handles supported scalar/array destinations. Every field is required, including fields with language defaults. The [supported-value matrix](https://github.com/carabistouflette/goose-json/blob/0061ec83bf7f88763402751d50e3c27f3dd13f68/README.md) excludes maps, null/optional values, enums and arrays of text or records. Supported arrays are numeric/bool. Input is capped at 1 MiB; float tokens at 128 bytes; encoding has no output cap. Failed decoding can partially update the destination.

**Recommendation:** retain goose-json for strict application records and document standard JSON for selective/dynamic protocol parsing. Ordinary JSON-RPC responses contain `jsonrpc`, `id`, and `result` or `error`; strict unknown-field rejection and absent/null alternatives make the current struct codec unsuitable as a general replacement for `rpc::result`. A dedicated envelope API or opt-in richer codec would address this without weakening existing strict behavior.

### TOML and logging: retain both choices

[Macho0x TOML](https://github.com/Macho0x/goose-toml/blob/589f168e70a2c83cb1e84cbf31ebee8d27c085c6/parse.goose) yields node trees with unescaped strings/keys borrowed from source and escaped strings in a caller-provided buffer. [Its porting notes](https://github.com/Macho0x/goose-toml/blob/589f168e70a2c83cb1e84cbf31ebee8d27c085c6/PORTING.md) explicitly omit writing, struct mapping and TOML 1.1 relaxations, and acknowledge possible one-ULP long-mantissa float differences. Carabistouflette's [TOML implementation](https://github.com/carabistouflette/goose-toml/blob/1014af21fda372a471ec4bde710a2e1989e05996/README.md) owns document data, supports 1.0/1.1, mutation and serialization, and documents input/node/depth/key-work limits and conformance campaigns. Its separate [source editor](https://github.com/carabistouflette/goose-toml-edit/blob/e053847ecfe983305080b70aa46632ac3ef9d783/README.md) preserves comments and untouched formatting for supported named edits. Borrowing versus ownership and read-only versus editing justify both listings; no common-contract speed comparison was run.

[Macho0x logger](https://github.com/Macho0x/goose-logger/blob/50695a3df0eb5a1048a4b183538d59f43f5eb279/README.md) supplies six severities, automatic UTC timestamps, explicit source file/line arguments, field builders and caller-buffer record formatting. [Sanitization source](https://github.com/Macho0x/goose-logger/blob/50695a3df0eb5a1048a4b183538d59f43f5eb279/sanitize.goose) applies regex and key-name rules, including credentials, webhook URLs, PEM keys and token-like strings. It is a heuristic: a blanket secrecy guarantee would be unjustified. Carabistouflette's [goose-log](https://github.com/carabistouflette/goose-log/blob/c29cdc27d41364e52e53556f8468d55552439bf6/README.md) instead keeps clocks, synchronization and output ownership with the caller, provides bounded byte escaping and explicit field masks, and reports sink outcomes. Its optional UTC adapter already exists, so adding timestamps is not an uncovered feature; automatic content-based secret detection is.

## Prioritized future work for carabistouflette

These are proposals, not implementation commitments. Priority reflects reuse across the existing library set, correctness risk and whether reuse of public work is preferable to duplication.

| Priority | Proposed work | Concrete acceptance evidence / dependency |
| --- | --- | --- |
| **P0** | Publish accurate discovery entries and disambiguate same-name crypto/HTTP/TOML packages | Pin provenance; identify HTTP fork/upstream; link both use cases; state Hyperliquid transport status, crypto timing caveat and exact JSON limitations. No implementation required. |
| **P1** | Design an opt-in broader JSON API for protocol envelopes | Specify null/optional, text/record arrays, maps or selective reads, unknown-field policy and output limits. Preserve strict default behavior. Demonstrate owned data, duplicate handling, malformed UTF-8, numeric boundaries and resource exhaustion with independent fixtures. Assess the standard reader before building another DOM. |
| **P1** | Evaluate bounded reusable HTTP POST and additional REST verbs | Current source only offers GET/POST, and reusable handles only GET. Specify PUT/PATCH/DELETE/HEAD, body rules, header ownership, origin/auth separation, cancellation and per-operation versus wall-time budgets. Verify connection-close/reuse and **no unintended replay of non-idempotent requests** with loopback HTTP/TLS fixtures. Prioritize this over building a second server stack. |
| **P1** | Assess reusable decimal and bigint dependencies | Pin Macho0x sources and a compatible compiler, define aliases/import layout and resource budgets; differential-test arithmetic, overflows, signed division, byte formats, rounding/normalization and exact protocol strings. Keep fixed decimal, arbitrary precision and U256 as distinct types. |

Define keys, sizes, nonce policy and error/zeroization limits. Require decompressed-output/work bounds and incremental behavior before accepting untrusted streams. Test truncation, dictionaries, checksum failure, trailing/concatenated members and output-limit boundaries. Keep tar path policy in goose-archive. |
| **P2** | Evaluate UUID and MessagePack reuse as independent modules | UUID needs explicit entropy/clock injection, platform entropy failures and counter semantics. ## Remaining uncertainties

- No build established that all packages work with one Goose compiler revision. Carabistouflette records compiler pins; many Macho0x quickstarts say only to install Goose and use sibling aliases such as `../crypto`. Import layouts and transitive root bindings must be qualified before recommending a runnable combined stack.
- The report identifies source behavior and public test artifacts, not a cryptographic audit, exhaustive protocol certification, sustained maintenance commitment or independently rerun CI result. In particular, Ed25519 verification equivalence and secret-dependent timing need dedicated work.
- Public repository metadata and default branches may change after this date. Full commit links preserve the inspected implementation; README version labels and remote dependencies do not by themselves prove a coherent released dependency graph.
- HTTP upstream/fork divergence, optional TLS/HTTP3 dependencies and every supported operating system were not independently audited. Preserve the projects' own platform qualifications and use the canonical upstream for future checks.
- No star counts, unmatched benchmark timings or “fastest” claims were used. The source contracts differ too much for an honest aggregate ranking.
